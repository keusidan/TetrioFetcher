# アーキテクチャ

## レイヤ構成

```
        利用者のコード
              │  Fetcher::user("Keusidan")
              ▼
┌─────────────────────────────┐
│ fetcher.rs   公開ファサード  │  型付きメソッド。ここだけ見れば使える
├─────────────────────────────┤
│ routes.rs    入力の正規化    │  pb→progression, 40l→40l_global,
│                              │  大文字→小文字, limit の丸め
├─────────────────────────────┤
│ transport.rs HTTP            │  スロットル, キャッシュ, リトライ,
│                              │  エンベロープ展開, HTML 検出
├─────────────────────────────┤
│ parse.rs     変換            │  生 JSON → 正規化モデル（全域関数）
├─────────────────────────────┤
│ jval.rs      寛容なアクセサ  │  42 / 42.0 / "42", -1, "z", JS sentinel
├─────────────────────────────┤
│ model.rs     出力型          │  Serialize のみ。snake_case で一貫
└─────────────────────────────┘
              │
              ▼ ch.tetr.io/api
```

## 各層の責務

### `fetcher.rs` — 公開ファサード

利用者が触る唯一の層。エンドポイントごとにメソッドがあり、
引数は人間が書きやすい形（`"pb"` や `"QuickPlay"`）を受けて内部で正規化します。

### `routes.rs` — 入力の正規化

「API がおかしい」と思われる報告の多くは、実はここの不一致です。

- `Gamemode::parse` — `40L` / `40lines` / `QuickPlay` などを受ける
- `PersonalBoard::parse` — `pb` / `global` などの別名を変換
- `RecordLeaderboard::parse` — 合成 ID を組み立てる
- `normalize_user` — 小文字化と危険文字の拒否
- `clamp_limit` — `1..=100`

**送信前に弾く**のが重要で、打ち間違いが「空の成功」に化けるのを防ぎます。

### `transport.rs` — HTTP

リクエストは次の順に流れます。

1. **キャッシュ確認** — 同じ URL で `cached_until` が未来なら通信しない
2. **スロットル** — 前回から 1 秒未満なら待つ
3. **送信** — `User-Agent`、任意で `X-Session-ID`
4. **判定** — 429 / 5xx ならバックオフしてリトライ
5. **デコード** — JSON でなければ `NonJson`、`success:false` なら `Api`
6. **記憶** — `cached_until` を保存

`404` / `422` はリトライしません。あれは「答え」であって障害ではないからです。

### `parse.rs` — 変換

すべての関数が**全域関数**です。壊れたフィールドは `None` か既定値に落ち、
レスポンス全体のパースを巻き添えにしません。

上流の1フィールドが改名されたときの被害を「1フィールド」に留めるための設計です。

### `jval.rs` — 寛容なアクセサ

型の揺れとセンチネル値を吸収する小さな関数群。
`as_i64` は `42` / `42.0` / `"42"` を受け、`as_stat` は `-1` を `None` にします。

### `model.rs` — 出力型

`Serialize` のみ実装。生成側の型なので、`Deserialize` は不要です。
`snake_case` で揃え、センチネルは解決済み、派生値（APP、平均 PPS）は計算済み。

## なぜ同期なのか

TETRA CHANNEL は素の JSON-over-HTTPS で、ストリーミングも双方向通信もありません。
非同期にする利点がほぼ無い一方、同期だと次の2つが**素直に書けます**。

- **スロットル**: 「前回から1秒」を `Instant` で持ち、そのまま `sleep` できる
- **バックオフ**: リトライ間隔をその場で待てる

非同期だと、これらをランタイムを跨いで正しくやる必要が出てきます。
この API は 1 req/秒程度を求めているので、間隔の正確さは実利があります。

非同期が要る場面（多数のユーザーを並行取得など）では、
`Fetcher` をスレッドごとに持つか、`Mutex` で包んでください。
内部に `RefCell` のキャッシュを持つため `Sync` ではありません。

## 依存が少ない理由

| クレート | 用途 |
|---|---|
| `serde` / `serde_json` | JSON |
| `ureq` | HTTP（`rustls` + `webpki-roots`） |
| `thiserror` | エラー型の導出 |

`rustls` を選んでいるのは、**システムの CA ストアに依存しない**ため。
proot / Android / コンテナなど、`/etc/ssl` が怪しい環境でも動きます。
